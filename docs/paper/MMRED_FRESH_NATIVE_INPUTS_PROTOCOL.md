# Fresh main-cohort native inputs and shared visual features

This stage consumes a complete, verified fresh cohort and prepares only its 1,400 main questions:400 N8,400 N16 and600 N32. The960 diagnostic questions remain metadata only. No model answer, performance-based selection, adapter update or training occurs. Root alone freezes sources and submits jobs, with at most one attempt per phase and one four-task CPU array. Preserve failures and partial outputs.

The six owned sources are stage_mmred_fresh_native.py, this protocol and four Slurm wrappers. Inherit the exact frozen fresh-data, original renderer, V3 native preparation and feature-extraction sources. Bind the fresh summary/plan and a passed original evaluation-feature summary supplied with --reference-features. Reference timings use feature/compact metadata, without predictions or fitted checkpoints.

Four phases are fixed:

1. CPU preparation:600 seconds, four cores,16 GiB. Select only the published main indices and preserve original seven-field renderer rows, system prompt, questions, typed answers, world identity and ordering. Inventory frames with the frozen Step/assignment/occupant-order identity. Assign row indices modulo four,350 worlds per worker. Each worker renders its needed keys once; duplicate keys across workers are counted and must produce identical PNG/pixel hashes. Publish main-by-length, N32 primary400 and N32 controls200 indices.
2. Four CPU render/compact workers:3,000 seconds each, four cores,16 GiB. Reuse frame2png and PNG inspection under the exact frozen renderer/font/package namespace. Preserve512px originals and call frozen V3 prepare_joint:392px native processing, images before the unchanged question, original four-axis positions/rope deltas and complete JSON/EOS targets. Omit only pixels from saved compact packets and verify every other tensor/metadata field after serialization. No CPU model load. At most7,200 render calls per worker before within-worker deduplication.
3. CPU merge:600 seconds, four cores,16 GiB. Verify all four shards, PNG/compact hashes, duplicate-key equality, original-row ownership and complete target inventory. No extra image decoding or tensor computation. Publish all1,400 inputs in original order and compute the visual-harvest resource forecast.
4. One B200 feature worker:3,600 seconds, four CPU cores,16 GiB host memory. Root schedules this alongside at most three other project GPUs. Load the unchanged native4bit model, preserve storage dtypes, freeze all parameters and install no adapters. Reprocess each image sequence and prove actual pixel/grid/compact/coordinate identity against CPU records. Invoke only the frozen visual extractor once per world; hooks require zero model/decoder/language/norm/head calls. Save nativeFP16[N*196,3584] postmerger features.

The exact main inventory is28,800 world-frame occurrences,5,644,800 feature rows and40,461,926,400 raw feature bytes before file overhead. Publish actual deduplicated PNG counts and serialized sizes. These are arithmetic counts, not measured runtime or storage-availability guarantees.

The fixed forecast is setup or measured elapsed time +1.25 times the sum over remaining worlds of (CPU staging maximum at N + feature-phase maximum at N), then60 seconds reserve. Initial feature-phase maxima/setup come from the passed original evaluation-feature metadata. Process the first original-order N8/N16/N32 worlds first, retain their outputs and count them once. Update the same maxima using those actual timings and replace setup with elapsed time; the remaining estimate must fit3,600 seconds. The estimate is empirical and deliberately overlaps some preparation/proof cost. A failed gate preserves those outputs and stops; no automatic continuation or remeasurement.

Final fields are rows_file, compact_cases_file, feature_index_file, populations_file and cases_file. The latter contains ordered {row,compact,features} records accepted by frozen training.load_inputs. Feature ownership retains index,sid,n,input_identity,compact,coordinate_identity,native_identity_sha256. Public verify_stage(summary,streaming=False) checks source/metadata lineage, feature ownership and the exact forecast; its default hashes compact/feature payloads. A streaming handoff defers those payload hashes to the actual consumer. Answer generation and checkpoint selection remain outside this stage.

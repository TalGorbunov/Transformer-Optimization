# A finite-precision witness for the symmetric local-code join

This fixed CPU diagnostic asks whether the existing 96-wide SUM/SiLU readout has a working parameter setting on all 216 orientation-training contexts when exact per-image person/requested-room codes are supplied. It neither fits parameters nor modifies any model initialization. The failed visual fits, their independent native-head audit, and all held native/confirmation gates remain unchanged.

The input and native identity come from the passed orientation preparation `check_443676` (plan SHA `d299d42a4444520f148f86252e2931ad599e03afac9edadbe9201836229bf097`). Independently parse every bound QA state and image occurrence in its 216 frozen rows. A local code is an unscaled one-hot person-by-ordered-requested-room coordinate among 18 coordinates, padded to 96; images outside the requested pair receive zero. The forward input contains neither the bag answer nor an intersection code. Gold labels are used only to audit the domain, construct the explicitly privileged reference route, and score predictions. Retain every input/code/frame inventory before numerical evaluation.

For each person the two half-counts `(a,b)` lie in `{(0,0),(1,0),(0,1),(.5,.5)}`. With `f(t)=SiLU(t)+SiLU(-t)=t*tanh(t/2)` and `c=tanh(.5)`, the expression `[f(a+b)-f(a-b)]/c` equals one exactly for `(.5,.5)` and zero otherwise in real arithmetic. Four hidden units per person, 36 total, implement this expression in the immutable `ParallelLocalJointCodeOracle` class. Set query weights, aggregate bias and unused aggregate rows to zero. The active aggregate rows are `+(a+b), -(a+b), +(a-b), -(a-b)`. Set the corresponding up-projection columns to `(+,+,-,-)*sqrt(96)*V_p/c`, where `V_p` is the original successful answer-code oracle's frozen column for person p. The reference is its original `sqrt(96)` answer code and frozen up-projection, from checkpoint `run_443295/final.pt`, accepted by precision report `443304`. The constants are computed once with Python binary64 `sqrt(96)/tanh(.5)`; scale the original FP32 columns in FP64 then cast once to FP32. No constant is selected from outcomes.

The construction is invariant to exchanging the requested rooms on this restricted count domain. It does not assert a Boolean join for arbitrary counts. It embeds the previously trained answer directions in the existing readout and thus establishes existence only, rather than learnability from the ordinary zero-up initialization or an unsupervised semantic representation.

Freeze and reload the four constructed FP32 tensors through a restricted checkpoint. Verify exact bytes, execute that actual existing class, and compare the resulting FP32 residual with the independent answer-code residual. Use the identical cached native global state in both routes; verify it byte-for-byte against the old answer-code global for each base scene. Cast each residual to FP16 before adding it to the FP16 global, then call the actual frozen native RMSNorm and linear head on `[1,B,H]`, with B=16 except the final B=8. All 216 rows are evaluated in their frozen order. There are exactly 14 constructed-core calls, 28 CPU norm calls and 28 CPU head calls, covering 432 head rows. No backbone, vision, GPU, generation, backward pass, optimizer, extra head route or parameter search is permitted.

Prospective numerical gates are componentwise residual `atol=1e-4, rtol=1e-4`, exact constructed/reference argmax agreement, and full-vocabulary probability total variation at most .02 between the two CPU routes. Both routes must independently predict the correct first token for **216/216 contexts and all 18 complete 12-context families**. This strong witness criterion is distinct from the earlier training screen. All raw logits, captures, residual errors, margins, calls and failures are retained. Accuracy, TV and residual differences are measured, not assumed from algebra. This selected-query CPU execution does not promise bitwise equivalence across backends, whole-name/EOS completion, visual feature sufficiency, generalization or deployed semantic labels.

One CPU Slurm allocation is allowed: four cores, 16 GiB, 300 seconds including source/input verification, saving and all numerical work. Model weights remain frozen. The summary is published last; its hash-only verifier checks source archives, dependencies and output bindings without importing tensors or repeating heads. No GPU or follow-on experiment is released by this proposal.
